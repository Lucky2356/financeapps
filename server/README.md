# Служба синхронизации

Один процесс, одна база, **ноль зависимостей**. SQLite, тестовый прогонщик и
вывод ключей — всё встроено в Node. Обновление на сервере это `git pull` и
`systemctl restart`, а не разбор того, почему сегодня не ставится очередной
пакет.

## Что она умеет и чего не умеет

Хранит зашифрованные книги и раздаёт их устройствам одного человека. **Открыть
их она не может**: ключ выводится из пароля на устройстве и на сервер не
уезжает. Украв эту машину целиком вместе с базой, нельзя узнать ни одной суммы
и ни одного названия счёта.

Видно другое, и лучше знать это заранее: сколько у кого книг, какого они
размера и когда их последний раз правили.

**Почты у службы нет.** При сквозном шифровании письма для сброса пароля
бесполезны — сбрасывает код восстановления, — а приглашение на десять человек
раздаётся лично. Значит: ни SMTP, ни «письмо не пришло», ни попадания в спам,
ни ещё одного чужого сервиса в цепочке.

## Что нужно

- **Node 22.6 или новее.** В Debian 13 штатный пакет старее, поэтому проще с
  nodesource:

  ```sh
  curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
  sudo apt-get install -y nodejs
  node --version    # должно быть 22.6+
  ```

  Флаг `--experimental-strip-types` в юните стоит не зря и на новых Node тоже:
  начиная с 23 типы снимаются сами, но флаг остаётся принятым и ничего не
  ломает. **Трогать юнит из-за версии Node не нужно.**

- Caddy, уже настроенный на ваш домен — он держит TLS.
- `sqlite3` и `jq` пригодятся для копий и приглашений:
  `sudo apt-get install -y sqlite3 jq`

## Установка

```sh
# Отдельный пользователь: службе незачем ходить дальше своей папки.
sudo useradd --system --home /opt/financeapps --shell /usr/sbin/nologin financeapps
sudo mkdir -p /opt/financeapps
sudo chown financeapps:financeapps /opt/financeapps

# Код.
sudo -u financeapps git clone https://github.com/Lucky2356/financeapps /opt/financeapps

# Пропуск управления. Только латиница и цифры — он ездит в заголовке HTTP.
openssl rand -base64 32 | tr -d '/+=' | head -c 40; echo

# Юнит.
sudo cp /opt/financeapps/server/financeapps.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl edit financeapps
```

`systemctl edit` откроет пустой файл — в него целиком, заменив «строку-из-openssl»
на то, что выдала команда выше:

```ini
[Service]
Environment=FINANCE_ADMIN_TOKEN=строка-из-openssl
```

Пропуск лежит здесь, а не в юните из склада: юнит приезжает с `git pull` и
перезаписался бы, а этот файл — ваш и остаётся на месте.

## Настройки

Всё — переменными окружения, в тот же файл `systemctl edit financeapps`.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `FINANCE_DB` | `./finance.db` | путь к базе |
| `FINANCE_PORT` | `8787` | порт (слушается только 127.0.0.1) |
| `FINANCE_ADMIN_TOKEN` | пусто | пропуск к `/admin/*`; пусто — управление выключено |
| `FINANCE_ORIGIN` | `*` | кому отвечать |
| `FINANCE_OPEN_REGISTRATION` | пусто | `1` — завестись может любой, кто знает адрес |
| `FINANCE_PUBLIC_URL` | пусто | каким адресом служба зовётся снаружи; нужен коду связки |
| `FINANCE_MAX_SLOTS` | пусто | сколько книг на человека; пусто — без предела |
| `FINANCE_MAX_MB` | пусто | сколько всего мегабайт на человека; пусто — без предела |

Умолчания подобраны так, что служба, поднятая без единой настройки, ведёт себя
ровно как раньше: пускает только по приглашениям и ничего не считает.

### Открытая запись

`FINANCE_OPEN_REGISTRATION=1` убирает приглашения: любой, кто знает адрес вашей
службы, заводит себе учётную запись сам. Это то, ради чего приложение вообще
можно раздавать людям «с улицы», — и это же чужие люди на вашей машине.

**Включайте её вместе с пределами.** Без них один человек занимает весь диск, а
кончившийся диск останавливает службу для всех, включая тех, кто ничего не
делал. Разумная пара для домашней машины:

```ini
[Service]
Environment=FINANCE_ADMIN_TOKEN=строка-из-openssl
Environment=FINANCE_OPEN_REGISTRATION=1
Environment=FINANCE_MAX_SLOTS=5
Environment=FINANCE_MAX_MB=50
```

Пять книг — это пять профилей («Личное», «Жена», «Бизнес»…), больше одному
человеку обычно не нужно. Пятьдесят мегабайт — это очень много операций: книга
на десять лет ведения занимает единицы мегабайт.

Что служба делает с упёршимся в предел: отказывает в записи кодом **507** и
пишет человеку, сколько ему разрешено и сколько он просит. Данные при этом
остаются на его устройстве целыми — не уехало не значит потеряно. Из
переполнения можно выбраться, убрав у себя лишнее: запись меньшего размера
поверх большей считается уменьшением, а не добавкой.

Поток новых записей с одного адреса ограничен десятью в час — иначе один
скрипт заводит тысячу учётных записей за минуту.

Какой это адрес, служба узнаёт так: заголовку `X-Forwarded-For` она верит,
только если запрос пришёл с 127.0.0.1 — то есть от Caddy на той же машине, — и
берёт из него **последнее** значение, дописанное самим Caddy. Первое пишет
клиент, и до 1.46.0 служба брала именно его: подставив случайный адрес, можно
было обойти все пределы — на регистрацию, на вход и на подбор кода связки.
Если посредник у вас не на той же машине, пределы будут считаться по его
адресу — то есть общими на всех. Держите Caddy рядом со службой.

Приглашения при открытой записи никуда не деваются: предъявленное приглашение
по-прежнему проверяется и гасится. Пустое поле значит «у меня его нет».

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now financeapps
systemctl status financeapps
```

Служба слушает **только 127.0.0.1**. Наружу она смотрит через Caddy — иначе к
ней можно было бы прийти по обычному HTTP в обход сертификата, и входной билет
уехал бы открытым текстом.

## Caddy

В ваш `Caddyfile`, внутрь блока домена:

```caddyfile
finance.ваш-домен.ru {
	# Поток событий нельзя копить в буфере: событие дошло бы через минуту
	# после того, как случилось. Отсюда flush_interval.
	reverse_proxy 127.0.0.1:8787 {
		flush_interval -1
	}
}
```

После правки: `sudo caddy fmt --overwrite /etc/caddy/Caddyfile && sudo systemctl reload caddy`

Проверка: `curl https://finance.ваш-домен.ru/health` — должно ответить
`{"ok":true}`.

## Первая проверка

Прежде чем идти в приложение, стоит убедиться, что служба живая. Три команды, и
каждая отвечает на свой вопрос.

```sh
# 1. Служба поднялась и Caddy до неё достучался.
curl -s https://finance.ваш-домен.ru/health
# {"ok":true}

# 2. Пропуск управления доехал до службы.
curl -s -X POST https://finance.ваш-домен.ru/admin/invite \
  -H "Authorization: Bearer ПРОПУСК"
# {"code":"..."}  — это и есть приглашение, оно пригодится дальше

# 3. Без пропуска внутрь не пускают.
curl -s -X POST https://finance.ваш-домен.ru/admin/invite
# {"error":"Нужен пропуск управления."}
```

Третья — не формальность. Ответь она кодом приглашения, это значило бы, что
завести у вас учётную запись может кто угодно, кто знает адрес.

Если первая отвечает пустотой или ошибкой Caddy, а `systemctl status financeapps`
говорит «active» — значит служба жива, но Caddy до неё не дотянулся: смотрите
порт в блоке домена и `journalctl -u financeapps -n 50`.

Если вторая отвечает «Нужен пропуск управления» с **правильным** пропуском —
значит `systemctl edit` не доехал: `systemctl show financeapps -p Environment`
покажет, что служба видит на самом деле.

### Что служба пишет в журнал

На каждый запрос — одна строка. Это первое, куда стоит смотреть, когда
устройство говорит «подключено», а данные не ходят: по журналу сразу видно,
дошло ли оно до службы вообще и что получило в ответ.

```sh
journalctl -u financeapps -f
```

```
GET /auth/params → 200 за 3 мс
POST /auth/login → 200 за 214 мс
GET /events → поток открыт
GET /vault → 200 за 1 мс
PUT /vault/… → 200 за 4 мс
```

Как это читать:

- **пусто, пока вы жмёте кнопки в приложении** — устройство до службы не
  доходит. Виноват адрес, сертификат или проксирование в Caddy, а не служба;
- **`→ 401`** — билет не принят: устройство считает себя подключённым, а служба
  его не узнаёт. Помогает отвязка и повторный вход в приложении;
- **`→ 409`** — «вас обогнали», это нормальная часть работы: два устройства
  писали одно и то же, приложение перечитает и сольёт само;
- **`поток открыт`** есть, а `PUT /vault/…` не появляется, когда вы заводите
  операцию на другом устройстве — не доходит запись, а не уведомление;
- **имени ячейки в журнале нет намеренно.** Вместо него `/vault/…`: имена ячеек
  — это названия ваших книг, и в журнале машины им делать нечего.

Проверка живости (`/health`) в журнал не пишет: Caddy дёргает её постоянно, и от
неё остался бы один шум.

### Служба поднимается и тут же умирает

`systemctl status` показывает постоянные перезапуски, а в журнале — трасса V8 на
сорок строк со словами `Check failed` и `SetPermissions`. Выглядит как поломка
службы, но почти наверняка виноват юнит: какое-то ограничение запрещает Node
делать память исполняемой, а без этого его JIT не работает.

Смотреть надо на `MemoryDenyWriteExecute`. В юните из склада её нет намеренно
(см. комментарий там же), но она могла приехать из вашего drop-in:

```sh
systemctl show financeapps -p MemoryDenyWriteExecute
```

Ответ `yes` — снимите: `sudo systemctl edit financeapps`, строка
`MemoryDenyWriteExecute=no` в блоке `[Service]`.

## Приглашения

Регистрация только по приглашению, и другого пути нет.

```sh
curl -s -X POST https://finance.ваш-домен.ru/admin/invite \
  -H "Authorization: Bearer ПРОПУСК" | jq -r .code
```

Полученный код человек вводит в приложении: **Настройки → Свой сервер**, вместе
с адресом службы, желаемым именем входа и **паролем своей книги**. Приглашение
одноразовое.

### Второе устройство — БЕЗ приглашения

Приглашение заводит учётную запись, а не устройство. Второй телефон или
компьютер подключается к той же записи, и нового кода для этого не нужно:
**Настройки → Свой сервер**, адрес, то же имя входа, тот же пароль книги, а
поле приглашения **оставить пустым**.

Пустое поле — и есть признак «я уже заведён, пусти». Выдай приглашение на каждое
устройство, их пришлось бы раздавать бесконечно, а на чужой телефон человек
завёл бы себе вторую, пустую книгу вместо своей.

Пароль здесь — **тот же самый, что у книги на первом устройстве**, а не новый.
Из него выводятся сразу две вещи: ключ, которым книга открывается, и секрет,
по которому служба узнаёт вас на входе. Поэтому другой пароль не даст ни того,
ни другого: служба ответит «Не подходит имя или пароль» и дальше не пустит.

Шкатулку с ключом книги второе устройство забирает со службы — больше ей взяться
неоткуда. Лежит она там запертой, и служба её не открывает, потому что нечем.

Кто уже заведён и сколько занимает:

```sh
curl -s https://finance.ваш-домен.ru/admin/people -H "Authorization: Bearer ПРОПУСК" | jq
```

Устройства человек смотрит у себя в приложении: «Настройки → Синхронизация →
Мои устройства». Там же он их переименовывает (`PATCH /devices/<id>`) и
выкидывает потерянный телефон вместе с его билетом (`DELETE /devices/<id>`).

## Код связки

`FINANCE_PUBLIC_URL=https://finance.ваш-домен.ru` — каким адресом служба зовётся
снаружи. Сама она этого не знает и знать не может: слушает 127.0.0.1, а имя
живёт в Caddy.

Зачем он нужен: устройство, на котором данные уже есть, просит у службы код
(`POST /pairing`) и показывает его крупно. На втором устройстве человек набирает
восемь знаков, и оно спрашивает у службы (`GET /pairing/<код>`), куда идти и под
каким именем. Остаётся ввести пароль — руками, и это единственное, что там
вводят руками.

**Пароля в коде нет и не будет.** Он — единственное, чем завёрнут ключ от
данных. Поехав в коде, а значит и в картинке QR, которую снимают из-за плеча
или пересылают в мессенджере, он сделал бы бессмысленным всё шифрование разом.

Что код отдаёт: имя входа и (если задан `FINANCE_PUBLIC_URL`) адрес. Больше
ничего. Живёт пять минут, срабатывает один раз, лежит в базе хешем; перебор
ограничен двадцатью попытками в минуту с адреса. Восемь знаков из алфавита без
похожих друг на друга — ни нуля с буквой О, ни единицы с I.

Не задан `FINANCE_PUBLIC_URL` — код отдаёт только имя входа, а адрес второе
устройство берёт тот, по которому само же и спросило. Выдумывать адрес из
заголовка `Host` служба не станет: заголовок приходит снаружи, и так она
отправила бы человека туда, куда её попросил чужой.

## Связка по картинке (с версии 2.0)

Приложение 2.0 подключает второе устройство **без имени и пароля**:

1. Первое устройство заводит запись одним нажатием: случайное имя, случайный
   секрет входа (`POST /auth/register` без приглашения — **нужен
   `FINANCE_OPEN_REGISTRATION=1`**). Иначе кнопка «Включить синхронизацию»
   ответит, что служба принимает только по приглашению.
2. Показывая QR, оно запечатывает ключ от данных одноразовым ключом и кладёт
   пакет рядом с кодом: `POST /pairing` с телом `{ "sealed": "…" }` (до
   16 КиБ). Одноразовый ключ едет только в картинке и на службу не попадает.
3. Второе устройство предъявляет код: `POST /pairing/<код>` с телом
   `{ "device": "Телефон (Android)" }`. Код гаснет, второму устройству
   заводится **свой билет**, пакет отдаётся и стирается из базы.

Билеты продлеваются, пока ими пользуются: устройству, связанному картинкой,
войти заново нечем.

Прежние ручки (`GET /pairing/<код>`, вход по имени и паролю) остались для
старых сборок приложения. База старой версии получает новый столбец при
запуске сама — обновление, как всегда, `git pull` и перезапуск.

## Копии

Содержимое книг и так зашифровано — копию можно класть куда угодно.

```sh
# Ежедневно, хранить 30 штук.
sudo -u financeapps sqlite3 /var/lib/financeapps/finance.db \
  ".backup /var/lib/financeapps/backup-$(date +%F).db"
```

**Бэкап рядом с сервером — не бэкап.** Копию надо забирать на другую машину.

**Непроверенный бэкап — надежда, а не копия.** Раз в квартал: взять вчерашнюю,
развернуть в пустое место, войти, сверить итог месяца.

## Обновление

```sh
sudo -u financeapps git -C /opt/financeapps pull
sudo systemctl restart financeapps
```

Схема базы досоздаётся при запуске (`create table if not exists`), ставить
ничего не нужно.

## Проверки

```sh
cd /opt/financeapps && npm run test:server
```

Зависимостей они не требуют — ни `npm ci`, ни сборки: прогонщик проверок
встроен в Node.

Служба поднимается на случайном порту с базой в памяти, и по ней ходят обычным
`fetch` — то есть проверяется ровно то, что увидит устройство, включая коды
ответов.

## Что стоит знать наперёд

- **Простой замечают все.** Приложение продолжит работать местно, но
  синхронизация встанет, и об этом скажут.
- **Потерянные коды восстановления.** Кто-нибудь однажды потеряет и пароль, и
  код. Ответ будет один — «книга потеряна», — и лучше, чтобы человек услышал это
  **при регистрации**, а не в тот день.
- **По ответу службы видно, заведено ли такое имя входа.** Для десяти человек по
  личным приглашениям это не та цена, ради которой стоит усложнять вход, но
  знать об этом надо.
